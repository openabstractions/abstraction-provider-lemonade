# Lemonade image provider package

*For installer maintainers.*

`lemonaded.exe` is the OpenAbstractions-owned image provider. Build the Windows x64 payload from this module with `go -C openabstractions-flat/abstraction-provider-lemonade/go build -trimpath -ldflags=-s -o <staging>/lemonaded.exe ./cmd/lemonaded`. The existing OA installer should place it at `tools/lemonaded.exe` as optional feature `lemonadeimage`. Installing the feature creates no engine process, model cache, or model download. The provider source and the OA installer carry the repository's Apache-2.0 license.

Lemonade is a separate upstream app. [windows-amd64.json](windows-amd64.json) pins its official 2026.39.1 portable Windows x64 ZIP, release source, archive and `lemond.exe` checksums, archive layout, Apache-2.0 license, and unsigned executable status. The verified archive includes `LICENSE`; extraction must preserve it beside `lemond.exe` and `resources/`. Its documented destination is a distinct versioned folder under `%LOCALAPPDATA%/OpenAbstractions/apps/lemonade/`. The app is selected and installed after the OA runtime, with the reviewed download/install plan. Existing personal Lemonade installations and their profiles are separate.

The beginner setup needs explicit activation of the reviewed Lemonade app, Vulkan backend, and approved BF16 model. After the catalog's separate install intent extracts the pinned app ZIP and public OA download jobs deliver the reviewed backend ZIP and three weights, the setup controller calls `lemonaded configure --activate-reviewed-package --package <installed version> --vulkan-backend-archive <reviewed ZIP> --bf16-main <approved DiT> --bf16-encoder <approved Qwen> --bf16-vae <approved VAE>`. Configuration checks the installed `lemond.exe` SHA-256, stages the pinned backend archive into that version's private cache, and moves the three weights by rename from the provider's download folder (`setup-info`'s `download_dir`, on the models folder's volume) into private model state, verifying each there; OA never copies a model for the engine, and a download on another volume is refused and kept. The saved per-user `selection.json` contains only the package ID of the selected version, explicit activation, and `user.LocalApprovedKlein`. Provider startup and every engine launch recheck the executable hash; provider admission requires the pinned backend cache so Lemonade cannot silently auto-fetch it in the beginner route.

Versions and updates (`research/lemonade-updates/DECISION.md`, VISION 2026-10-01). `server.Packages` in `go/server/package.go` lists every Lemonade version this build can run, one entry per `lemonade-engine` pin of `monitor/internal/setup/install_pins.json` for Windows x64: version, archive and program SHA-256, the package manifest, the paired sd.cpp and llama.cpp manifests, the paired image backend archive SHA-256, the model revision, and the locked config. The table only grows; `known_packages` in [windows-amd64.json](windows-amd64.json) lists the same entries, and Setup's `lemonade_pins_test.go` refuses a pin the table does not know or pairs differently. The selection names the active entry. Each launch reads the selection and resolves the entry immediately before it proves and holds the files; a run in progress finishes on the version it proved, and the next launch runs the newly selected one. Each version owns `engine-cache/<version>` (its paired backends under `bin`), `engine-config/<version>` (its locked `config.json` and the model registry) and `engine-files/<version>` (its engine-file records); `engine-models`, `store`, `content-records.json` and `selection.json` are shared. Setup moves the selection through three verbs, and nothing else calls them:

- `lemonaded package check --version V --root DIR --json` proves the tree Setup staged at `DIR` against V's manifest with the full hash, changes no ACL, record or selection, and prints `{"version":1,"ok":true,"backend_archive_sha256":…,"model_revision":…}`, the pairing Setup compares with its catalog.
- `lemonaded package activate --version V [--vulkan-backend-archive ZIP] [--llamacpp-backend-archive ZIP] [--replace-backend]` proves V's installed package, stages V's paired backends into V's cache (from a named archive, or copied from the selected version's proven folder when the pairing names the same build), writes V's config folder, checks that the private model's revision is V's (otherwise it names `--replace-private-model` through Setup's model step), installs V's engine files, and writes the selection last under the setup lock. With the selection already at V it proves and returns without copying. A copy a killed activation left beside V's backend folder is removed before the next copy. A private model of another revision and a selected V whose engine files are not installed are refusals (exit 2). It prints `{"version":1,"ok":true,"active_version":"V"}`.
- `lemonaded package retire --version V` refuses the selected version, exits 3 with `held` on stderr while a launch holds V's files, and otherwise removes V's cache, config folder and records. The package folder is Setup's to remove; the private model, the store and the selection stay.

A refusal of a package verb exits 2; any other failure exits 1. A provider root from before per-version folders (`engine-cache/bin`, `engine-config/config.json`) verifies incomplete; Setup's engine-files step (`configure --activate-reviewed-package --engine-files-only`) moves those folders under the selected version, removes the records bound to the old paths and installs the engine files again, without reading the private model.

Each launch applies the conditions of the three security reviews in `research/security-reviews/` (Lemonade 2026.39.1, stable-diffusion.cpp master-843-462d675, llama.cpp b10825, the build Lemonade 2026.39.1 pins):

- Package: all nine files of the extracted Lemonade package, including `resources/backend_versions.json` and `resources/defaults.json`, are pinned by `server.Lemonade2026391` in `go/server/package.go`; any other file or folder in the package refuses the launch.
- Backends: every file under the selected version's `engine-cache/<version>/bin` is pinned by the reviewed manifests in `go/server/manifest.go` (21 sd.cpp files; 52 llama.cpp b10825 files, of which `ggml-rpc-server.exe`, `ggml-rpc.dll` and the command-line tools must be absent). Any other file, folder or variant is refused. `configure --llamacpp-backend-archive <llama-b10825-bin-win-vulkan-x64.zip>` stages the llama.cpp archive by its pinned size and SHA-256 and writes only the 24 files the review keeps; Lemonade starts `llama-server.exe` from that folder and sets it as the working directory.
- Both are proven through the shared facade `programfiles` owner (facade CONTRACT.md INF-F1..INF-F7). `configure` hashes the package and backend folders, gives every folder the read-only ACL and writes metadata records under `engine-files/<version>`. Each launch checks those ACLs, hashes every file at the first launch of the provider process and after any refusal, and otherwise checks each file's ID, size and times against the record. The files stay open with read sharing only until Lemonade's process tree exits. A setup made before this check lacks the ACL: its launches refuse and name `lemonaded configure --activate-reviewed-package --engine-files-only`, and `verify-setup` answers `verified: false`, which brings the guided step back; Setup then runs that step. The engine-files step stages each named backend archive, proves the package and backend folders and installs them, and never reads or copies the private model. A plain `configure` re-run keeps a staged backend and model that verify, copies nothing, and ends by installing the engine files. `--replace-backend` replaces a backend folder of another build, such as llama.cpp b10723; `--replace-private-model` stages the model again from its downloads and replaces no backend. `lemonaded engine unlock` gives the package folder of every known version and every backend folder back to the account for removal; the Windows uninstaller runs it before `lemonaded` goes, and Setup unlocks a retired package version before it deletes its files.
- Keys: two random 256-bit keys per launch reach `lemond` only as `LEMONADE_API_KEY` and `LEMONADE_ADMIN_API_KEY` in its environment. Every provider request carries one of them, which closes `/internal/*` and the model API to other local processes and web pages.
- Environment: built from nothing: `SystemRoot`, `windir`, `SystemDrive`, `PATH` limited to the Windows system folders, `TEMP` and `TMP` at `engine-temp`, and the two keys. `GGML_*` (`GGML_BACKEND_PATH` loads the DLL it names), `MTMD_*`, `LLAMA_*`, `HF_*`, other `LEMONADE_*` and proxy names are refused even if the allow-list names them. Lemonade starts `llama-server` and `sd-server` with this block unchanged, so the engines inherit exactly these names, the two keys included.
- Configuration: `engine-config/<version>/config.json` must equal the locked bytes of the version's config function, `server.LockedConfig` for 2026.39.1 (loopback host, no broadcast, offline, no executable fetching, every backend `*_bin` built in and every `*_args` empty; a backend argument or a forbidden llama.cpp option in it is refused before it is written). Any other file in that folder except `user_models.json` refuses the launch, and so does any entry of the version's cache folder other than `bin`, because Lemonade moves legacy `config.json`, `jobs.json`, `recipe_options.json` and `user_models.json` from its cache folder into its config folder at every start.
- Arguments: the command line is the private folders, `--port`, `--host 127.0.0.1` and `--no-broadcast`, checked against an allow-list.
- Weights: safetensors or GGUF only, in the models folder and in the model registry.
- Network: after readiness and around each request, every socket of the contained process tree must be on 127.0.0.1 or `::1` and the tree must hold its listener on `127.0.0.1:<port>` (`abstraction-identity` `CheckLoopbackOnly`, `ID-T7`); otherwise the tree is stopped.
- Routes: callers reach only `POST /api/v1/images/generations`, `POST /api/v1/images/edits` and, behind the chat gate below, `POST /api/v1/chat/completions`. `/internal/*`, `/mcp`, pull, install, `/api/v1/load` and the Ollama routes stay closed. An image request is read once it holds the provider's request slot, bounded by two input images of `MaxImageBytes` (default 20 MiB) and the text fields, and checked through `providerhost/sdcpp` (inference CONTRACT.md INF-SD1..INF-SD3). Only `model`, `prompt`, `n`, `size`, `response_format` and the edit files `image` and `mask` are forwarded, each once. `<sd_cpp_extra_args` in any text value, which `sd-server` would read as generation parameters with unchecked LoRA paths, a size beyond 64..4096 per side or 2048 × 2048 pixels, an input image whose header names such a size, a transfer-encoded or repeated part and a file other than a PNG, JPEG or WebP are refused before Lemonade sees the request. The provider forwards its own encoding of the checked fields. A declared model that resolves to a Lemonade collection (the built-in Omni collections by name or `builtin.<name>` alias, an `extra.*` model, or a `user.*` model with a `collection.*` recipe) refuses the provider's configuration and each launch with `engine:collection-model`, because an Omni collection's tool calls reach `sd-server` past these checks.
- `sd-server` has no authentication of its own: a local process that learns its loopback port can submit image work to it directly. The provider's keys protect Lemonade's routes only.

Chat route through llama.cpp b10825. The provider forwards a chat request only while all five conditions of the llama.cpp b10825 review that apply to Lemonade hold; otherwise it refuses with `engine:chat-route:<condition>`:

- `engine-files`: the llama.cpp folder is the reviewed b10825 manifest, proven and held for the running launch.
- `load-options`: the request carries no load option (`ctx_size`, which Lemonade takes from a chat body, any `llamacpp_*` or other `*_args`, `*_bin`, `*_backend`, `*_device`, `save_options`, `recipe_options`, Ollama `options`); the locked config carries no backend argument; `recipe_options.json` and a registry `recipe_options` field refuse the launch.
- `environment`: the environment of the launch, which `llama-server` inherits, passes the allow-list and the forbidden names.
- `media`: an image must be a base64 `data:` URI holding a PNG or JPEG of at most 16 megapixels; the provider decodes it and forwards its own 8-bit PNG in its place, so llama.cpp parses only provider-produced image bytes. Audio (`input_audio.data` as raw base64 or a `data:` URI, `input_audio.url` as a `data:` URI) must be WAV, MP3 or FLAC as llama.cpp recognises it. `http(s)://` and `file://` URLs, video, WebP and every other image are refused before Lemonade sees them, because llama-server fetches any URL a chat names and decodes video, WebP and images its decoder rejects by spawning FFmpeg, and no FFmpeg build is reviewed.
- `llama-flags`: no forbidden llama.cpp option (`--sleep-idle-seconds`, `--host`, `--rpc`, `--tools`, `--agent`, the MCP, Hugging Face, Docker and URL options, `--models-dir`, `--media-path`, `--path`, the log and slot paths, `--video-ffmpeg-dir`, `--cors-origins`) is in any argument path the provider controls.

The forwarded body is the request as the provider decoded it, encoded again, so Lemonade parses exactly what was checked. CVE-2026-43631 and CVE-2026-43632 (vocabulary use-after-free and tokenization races around `--sleep-idle-seconds`) remain unfixed in b10825; the guard is that no path passes `--sleep-idle-seconds` and Lemonade 2026.39.1 passes none. OA callers reach the chat route once setup offers a reviewed chat GGUF with a pinned SHA-256 (review condition 4) and the provider declares a chat model; until then the selection holds only `user.LocalApprovedKlein`.

Speech through whisper.cpp and Kokoros (`research/security-reviews/whisper.cpp-v1.8.4-win.md`, `kokoros-b17-win.md`). The provider serves `transcription@1` with `Whisper-Large-v3-Turbo` and `speech@1` with `kokoro-v1` over the same native endpoint as image work (`providerhost.NewEngine`). The installed declaration (`installer/declarations/lemonade-image.json`) names both profiles and models; admission refuses an unstaged profile `engine:audio:engine-files` or `engine:audio:model-files` before Lemonade starts:

- Isolated installs: every `lemonaded` command takes `--state DIR` (the provider state folder: selection, engine cache, config, models, engine-file records) and `--dir DIR` (the folder holding `<version>\<archive root>\lemond.exe`); the defaults stay `%LOCALAPPDATA%\OpenAbstractions\providers\lemonade` and `%LOCALAPPDATA%\OpenAbstractions\apps\lemonade`. A live test stages under both and removes them afterwards. Each must be a local folder, never a UNC share, a device path or a network drive; an absent one is created private to this account, and an existing one must already be private (abstraction-identity's `go/privatedir`, identity ID-D1: this account's, no access for other accounts but SYSTEM, no link or junction). Every existing parent below the volume root must be owned by this account, SYSTEM or Administrators. With `--state`, `serve` listens at an endpoint derived from the account and the state folder's identity (volume serial number and file ID, the same for every path that reaches the folder), so two isolated installs never share one, and `serve --endpoint` is refused; without it the per-user endpoint is unchanged. A speech-only selection serves with no image model.
- Speech without the picture setup: on a state folder with no selection, `--speech-only` needs only the installed reviewed Lemonade package; it stages the speech files, installs the package's engine files and saves a selection with no models. Its launch requires no image backend; the first `configure` form adds the picture model to it later, and Setup's probe reads it as an image setup still to run. Without the package it names the version, its program path and `--dir`.
- Files: `configure --activate-reviewed-package --speech-only` stages whisper.cpp v1.8.4 Vulkan (`whisper-v1.8.4-windows-vulkan-x64.zip`; CPU is the documented alternative) and Kokoros b17 (`kokoros-windows-x86_64.tar.gz`, top folder stripped as Lemonade strips it) by their pinned SHA-256, keeps only `whisper-server.exe`, `whisper.dll` and the ggml libraries (never `SDL2.dll` or the command-line tools) and all 365 Kokoros files, and moves `ggml-large-v3-turbo.bin`, `index.json`, `kokoro-v1.0.onnx` and `voices-v1.0.bin` by rename into the models folder's Hugging Face layout, each checked against its pin; a refusal moves each back. Each launch proves and holds these folders as it does the package (INF-F1..INF-F4). The speech models are admitted by their exact paths, never by extension; an `index.json` anywhere else, the NPU `.rai` cache and a `whispercpp/npu` folder refuse the launch. A missing Kokoros model keeps the speech route closed, so `koko` never downloads one.
- Configuration: the locked `config.json` names `whispercpp.backend` `vulkan` explicitly (never `auto`, which can choose the refused NPU build) and keeps every whisper.cpp and Kokoros `*_bin` built in and `*_args` empty. A `config.json` holding exactly the previous lock, which named no whisper backend, is replaced in place.
- Working directory: Lemonade starts in the proven, held package folder; `whisper-server` and `koko` inherit it, so the relative path whisper-server can read from request bytes (W1) and `espeak-ng-data` lookup find only pinned files.
- Environment: `WHISPER_*`, `OVERRIDE_VITISAI_*`, `KMP_*`, `PIPER_*`, `ESPEAK*`, `ORT_*` and `SSL_CERT_*` are refused besides the names above.
- Image routes: an image request whose `model` is absent or no declared image model is refused `request:engine-form` before Lemonade sees it, so an image call never makes Lemonade load `Whisper-Large-v3-Turbo` or `kokoro-v1`.
- Routes: only `POST /api/v1/audio/transcriptions` and `POST /api/v1/audio/speech` are added, and only while the launch holds the package folder, the route's backend and model folders, the explicit backend and a clean environment; otherwise the refusal is `engine:audio:<condition>` (`package`, `engine-files`, `model-files`, `backend`, `arguments`, `environment`, `backoff`). A transcription is `audio.wav`, the provider's own 44-byte-header WAV of the caller's 16-bit PCM WAV (at most 16 MiB; other formats read `unsupported_feature`), `language` from whisper's table, and no other whisper-server field; the answer is read with a 4 MiB cap as JSON. A speech request carries English voices only (`af_*`, `am_*`, `bf_*`, `bm_*`), NFC text without control characters, `response_format` `pcm`, `speed` 0.5..2.0 and `stream` false, never `initial_silence`, `lang_code` or load options; the PCM answer (at most 64 MiB) gets the provider's own WAV header.
- Crashes and idle: a speech request whose connection drops or whose engine fails is never resubmitted; the provider logs the input's SHA-256 only and refuses speech, and speech only, for a backoff of 5 s doubling to 5 minutes; it stops the tree, so koko starts afresh, only when no request is in flight and no other model has work in the provider. Each stop checks the launch, the request slot and the provider's work and stops the tree in one hold of the server's lock, so an admission that arrives meanwhile starts the tree again after the stop. Once the tree has served audio, it stops five minutes after a request last reached or left it when no request is in flight and no declared model has an admitted or running operation; the next admission starts it again.

Stated exposure. `whisper-server` has no authentication and answers `Access-Control-Allow-Origin: *`; `koko` has no authentication, answers any origin and parses `text/plain` bodies as JSON. While either runs, any local process or account and any browser page that finds its loopback port can transcribe or synthesize directly, bypassing the provider's checks: through whisper-server it can read local audio files and make Windows open SMB or WebDAV connections with the account's credentials (W1, a request file read as a path), load any file through the memory-unsafe legacy ggml loader and stop the engine (W2, `/load`), and exhaust memory through the cpp-httplib 0.20.0 advisories; through koko it can exhaust memory (K1, `initial_silence` and an unbounded body), select espeak-ng files by `lang_code` (K2) and send text to espeak-ng 1.52.0.1's known parsing defects (K3). The provider's keys protect Lemonade's routes only. W1 and W2 belong reported to `lemonade-sdk/whisper.cpp-rocm` (W2 also to `ggml-org/whisper.cpp`), K1 and K2 to `lemonade-sdk/Kokoros`; OA-built engines without these surfaces are the step before speech ships beyond the owner's machine. `koko.exe` and `espeak-ng-data/` are GPL-3.0-or-later: OA never ships them; Setup downloads them from the publisher with consent text naming that licence.

A launch refusal answers admission with a typed reason (`engine:package-unavailable`, `engine:backend-unavailable`, `engine:config-mismatch`, `engine:weight-format`, `engine:collection-model`, `engine:listener-not-loopback`, `engine:launch-plan`, `engine:audio:<condition>`) and writes the full error to the provider log. A chat refusal is the provider client's error, a `server.ChatRefusal` that `server.RefusalReason` maps to `engine:chat-route:<condition>`. An arbitrary executable can be used only through the separately labeled advanced flags. These downloads and staging belong after the core installer transaction and require their own review and progress. The qualified BF16 model's derived private path is checked against this Lemonade build's observed Windows legacy path limit before activation.

Card lease and GPU faults (resource CONTRACT.md RES-L1..RES-L4 and RES-G1..RES-G7, VISION 2026-10-01). The installed declaration names `card:0`, so the runtime writes `lemonaded`'s hold rules through its one card-rules writer. Each launch of the tree runs through the resource kit's `holder` (`go/provider/card.go`): the backend proof, then a lease of `card:0` for the declared models' pinned sizes (`server.AdmissionEstimate`; `--card-bytes` in advanced mode), then Lemonade's start and readiness. The lease is bound to Lemonade's process, renewed every 8 s and released when the tree stops: after 5 idle minutes with no admitted, running or retained operation, on a yield answered while no operation is active, and when `lemonaded` exits. A lease the resource service ends during readiness stops the tree, which loads once more; a second end refuses `lease:ended`. A refused lease reads `lease:not_permitted`, `lease:insufficient`, `lease:holders_refused` or `lease:unavailable`. The `gpufault` Guard refuses a launch `gpu:standby` or `gpu:resetting`, stops the tree and releases its lease on a driver reset, and writes each fault as one OA log record and one stderr line; its quarantine is `gpu-quarantine.json` in the provider state. The Guard is the resource kit's provider composition (`gpufault.ForProvider`) and the lease words are `holder`'s. The lease service is the one `ABSTRACTION_RESOURCE_ENDPOINT` names, else the installed runtime's. The provider takes no wake lease (TODO D2). Still open: reading the engines' device-lost lines (TODO D1), the sd.cpp dispatch row's `--diffusion-fa` for sd-server (D1a) and quarantining the request that was running (D1b).

The fixed installed CLI exposes `setup-info --json` for a cheap read-only result, reply version 2: `provider_root`, `provider_id` (`lemonade-image`), `selection_present`, `active_package` (`version` and `program` of the selected version, absent without a selection) and `known_packages` (each table entry's `version`, `archive_sha256`, `program_sha256`, `backend_archive_sha256` and `model_revision`, in table order), `staged_models` (the picture models the selection serves, the starter model first) and `download_dir` (the folder Setup downloads model files into, on the models folder's volume). A selection file that names no known package makes it exit nonzero. Presence is not a verified setup claim; Setup checks the active package against the version its journal names as installed. `setup-probe --json` hashes the three private BF16 model files and returns `complete` for exact model staging; `verify-setup --json` returns `verified` only after checking the selection, exact installed app, Vulkan backend, and model snapshot. Partial or mismatched state makes either deep probe exit nonzero without a success object. These commands do not start Lemonade or download anything. The Panel calls the fixed installed `tools/lemonaded.exe` with those exact verbs, so it need not derive provider-private paths.

Once selected, installed `lemonaded.exe` starts with **no arguments**, or with the MSI declaration's `serve --endpoint {endpoint}`. It reads the selection, derives `openabstractions.exe` next to itself as its sole designated runtime, allocates a private loopback port, and binds the runtime-designated local endpoint. Guided registration uses the same `lemonade-image` identity as the declaration. Content store and Lemonade cache/config paths stay under the provider's per-user state root. Only an admitted image request starts its selected Lemonade child. Explicit engine and state path flags remain an advanced/test route.

The pinned upstream portable `lemond.exe` passed isolated authenticated health, full model inventory, and graceful shutdown with this provider. It also generated a real 512×512 four-step BF16 image on the Radeon 8060S with sd.cpp Vulkan `master-843-462d675`: startup/readiness 0.719 s, model load 5.735 s, image request 56.237 s, 278,521-byte PNG SHA-256 `5abe784296dfa13cc51a5a4cb8061fc69c3365c7f66b987e728f54895d18555f`. A following 40-step request canceled after one second and the contained process tree stopped within 10.312 s. A separate OA-mediated first authorized request from stopped provider/engine completed on first attempt in 20.437 s using a previously cached backend. These timings are individual receipts, not a speed comparison. The package remains a reviewed local candidate, not a published 0.4.0 release.

Uninstalling OA removes `tools/lemonaded.exe` with its optional feature. Removing the upstream portable app deletes only the exact versioned app folder after it stops. Provider state, downloaded model weights, and generated images remain until the user separately chooses to remove them.
